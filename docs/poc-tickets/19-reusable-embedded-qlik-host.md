# 19 — Build the reusable embedded Qlik host and token bridge

**What to build:** One native WebView host shared by the Agentic Assistant and, later, the Analytics App surface, using only the auth path chosen and approved in ticket 15. This ticket delivers a host that loads the embed and keeps it signed in for a full session; navigation, storage and sign-out hardening are ticket 24.

**Blocked by:** Ticket [15](15-record-embedded-auth-spike-outcome.md) — path (a) chosen 2026-10-02, so this is unblocked for code; iOS and physical-device evidence is carried here. If it had selected the Qlik-web-page fallback instead of native-token reuse, the token-bridge criteria below are replaced by that fallback's.

**Status:** in-progress — host code and unit tests landed (`src/qlik-embed/`); no device evidence yet, and nothing mounts the host until ticket 21

**Progress 2026-10-02.** The host pulls a token from the app on every use (the page asks over `postMessage`; the app replies only to the current session), so expiry and refresh come from `getAccessTokenWithExpiry`. Session failure is detected from a token the app cannot supply, a main-frame load error and a top-frame navigation away — the last is unproven on Android, where the spike saw that hook miss the login redirect. `qlik-embed` documents no fatal-error event, so none is wired — confirm on device whether the runtime surfaces one. Sign-out teardown of an already-open page is ticket 24. The host also sets `incognito`, `cacheEnabled={false}` and dev-only WebView debugging, which ticket 24 still has to verify on device. Known small limits: request ids restart on an in-page reload, array-form `Authorization` headers are not detected, and the availability check keeps the old host mounted while a Tenant change re-resolves. Internal builds (`__DEV__`) log a device-validation trace to the Metro terminal — token requests with their remaining lifetime, navigations (origin and path only), blocked navigations, load errors and session failures, and on sign-in the requested and granted OAuth scope — never tokens, query strings or Answer content. Each token request is labelled `runtime`, `api` or `exchange` (page-asserted, trace only), so a device log can show the runtime's `/oauth/token` exchange happened during a long session; messages the host drops (wrong page URL, malformed) are traced too, because a platform reporting a different page URL would otherwise show nothing. Device finding (Android, offline at load): the inline page loads without internet but Qlik's script cannot download, no WebView error fires, and the host sat on a blank screen forever. The page now reports a failed script download (`load-failed`), and an embed that makes no token request within 20 seconds counts as a failed load, both ending in the "could not load" guidance with Try again; to be re-verified on a device. Internal builds also have an "Expire token now (test)" button in Settings: it marks the stored expiry as reached so the next request refreshes with the real refresh token. It exercises only the app-side refresh — Qlik's server-side expiry and how the runtime reacts to a rejected old token are not covered, so the "survives past expiry" criterion stays open; with no refresh token the next request ends in the sign-in guidance. Scope evidence so far: the emulator spike streamed chat with only `user_default offline_access` requested, so no scope has been added; the granted scope string is still to be captured on a device. **iOS device verification is still to do** — no Apple Developer account and no Xcode machine yet. Device validation proceeds Android-first on a physical phone; the iOS run (including whether `event.nativeEvent.url` from an `html`-source WebView matches `isOwnPage`, which would make the host ignore every token request if not) waits until a machine with Xcode is available. Android alone does not close the iOS criteria. Still open: scope verification, the expiry/resume and long-session device checks on iOS and Android, deleting the spike (kept as the reference until a device run proves the host; it has no consumer to run it before ticket 21), and the final lint/tsc/test gate with device evidence.

- [x] For native-token reuse, use the existing `getAccessToken(config)` authority. Tokens and generated HTML remain in memory; no backend, API key, client secret, refresh token in page JavaScript, or browser token store is introduced
- [x] The host reproduces the spike-demonstrated behaviour: the page's origin is the tenant, the runtime's same-origin `fetch` calls carry the bearer token except calls under `/oauth/`, and the runtime's `POST /oauth/token` exchange is answered locally. Escape interpolated configuration and identifiers for their actual HTML/JavaScript context
- [x] The locally answered exchange returns a **fresh** token obtained from the native app on each call, with an `expires_in` taken from the token's actual expiry, not the load-time token or a hard-coded value. The same token source feeds the bearer on calls
- [ ] The native-to-page token bridge validates messages, binds replies to the current trusted page and session, and rejects stale requests after sign-out or Tenant change
  - Partly true: messages are validated and bound to the session, and a Tenant/client/target change remounts the host. Sign-out is not observed by a mounted host — later requests are refused only because the token source returns nothing, and a page already holding a token keeps it until ticket 24's teardown. The trusted-page check also accepts `about:`/`data:` and relies on `nativeEvent.url`, which is unverified on iOS and for subframes
- [ ] Verify Agentic AI permissions and Native OAuth granted/requested scopes for the Assistant. If the existing `user_default`/`offline_access` request is insufficient, add only the proven required scopes and record re-consent/re-authentication needs for ticket 23's runbook
- [ ] Token expiry uses actual expiry metadata, not a hard-coded six-hour lifetime. Prove that a session survives past the access token's expiry and an app resume; when silent refresh fails, show actionable native re-authentication guidance without a login redirect or retry loop
- [ ] Unexpected runtime behaviour — a navigation to a Qlik login page, a fatal embed error, a failed exchange — is treated as session failure with native guidance, never an interactive login inside the WebView unless ticket 15 approved that fallback
  - Unproven on Android: ticket 15 saw `onShouldStartLoadWithRequest` miss the redirect to the Qlik login page there, and it is the only navigation detector in the host. Needs the redirect device test from ticket 24 before this counts
- [x] Handle only the traffic observed in the spike (`fetch`). Document that WebSocket or XHR use by the runtime is not covered, and the manual device check to repeat after Qlik runtime updates, because the runtime is downloaded from the tenant and can change without notice
- [x] The host is unreachable on web, including direct routes; web previews stay on fixtures. App-wide screen-capture protection remains active
- [ ] After the host works, delete `src/app/agentic-spike.tsx` and its header link/Stack registration in `src/app/_layout.tsx`, preserving unrelated local edits. Do not delete earlier; the spike is the reference until then
- [ ] Tests verify the chosen auth seam, the bearer/exchange decisions (including the `/oauth/` exclusion) and fresh-token delivery. Device evidence verifies refresh/expiry and a long chat session on iOS and Android; `npm run lint`, `npx tsc --noEmit`, `npm test` pass

**Decide during:** Whether the page asks the app for a token on every call (through `postMessage`) or the app pushes renewals into a long-lived page; mid-session expiry UX; whether unsent input can survive re-authentication in memory. Do not promise input restoration the Qlik-owned surface cannot provide.
