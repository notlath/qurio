The problem

How can MTC recreate essential Qlik Analytics functionality in a customizable application, while integrating an AI-powered conversational experience through Qlik Answers?

Problem

Qlik's mobile app is strong for dashboards. Its store listings and mobile help do not mention Qlik Answers. Qlik supports Answers chat in mobile browsers, but a no-browser-access requirement rules that route out.

A native app that signs each person in to their own Qlik Cloud Tenant and puts Assistants and Analytics Apps in one place, in an interface MTC can tailor.

Expected value

One place to ask and to look. Answers cite their sources. Access stays governed by the permissions Qlik already enforces.

System architecture

Objective · 7 min

Show that the architecture is simple and keeps Qlik in charge of data and permissions. Distinguish MTC's parts (green) from Qlik's (grey).

Walk the four flows

  1. Sign in. The app opens the OS sign-in sheet on Qlik's login page (OAuth 2.0 authorization code with PKCE, public Native client, no secret). Redirect: qlikanswers://auth. Scopes: user_default, offline_access. The access token stays in memory. The refresh token and its expiry go to SecureStore (Keychain / Keystore, this device only). Before each call the app refreshes silently with a 60-second margin. Concurrent calls share one refresh, because Qlik rotates refresh tokens. Sign-out revokes both tokens.
  2. Ask. The Qlik adapter calls /api/v1/assistants/<id>/threads/…/actions/stream. The stream is concatenated JSON. A parser in the app handles it and shows text as it arrives. Lists use /api/v1/items (Analytics Apps) and /api/v1/assistants. All screens use MTC's own domain types, never raw Qlik JSON (ADR-0006).
  3. Agentic UI. A WebView loads Qlik's own qlik-embed web component. The app gives it the person's own access token. Same-origin fetch calls get a bearer token. The runtime's token exchange is answered inside the app. This is a workaround, not a Qlik contract (ADR-0009).
  4. Analytics engine. For an Analytics App, the engine WebSocket needs a short-lived token. The app requests it natively from /oauth/token (about 90 seconds life), because the WebView's request is rejected (OAUTH-29).

Other facts

  • The qlik-embed script loads from jsDelivr at major version 1. It is not pinned to an exact release.
  • Errors map to clear states: Offline, Signed out, Busy (HTTP 429 with Retry-After), No access, Tenant Approval required (OAUTH-28), and more.
  • Pagination links are followed only if they stay on the configured Tenant, so the token never goes elsewhere.
  • The web build exists for development only. It uses sample data and cannot reach Qlik (ADR-0005).

Security and access management

Qlik decides who sees what. The app protects the device.

Controls in the app · verified in code

  • Per-person sign-in: OAuth 2.0 with PKCE. No shared account, no client secret, no backend.
  • Access token in memory only. Refresh token in the device keystore, this device only.
  • Sign-out revokes both tokens at Qlik, then clears them locally.
  • The token is sent only to the configured Tenant.
  • No Answer content stored. Embedded view runs incognito with cache off.
  • Privacy lock on by default. Screenshot and recording protection in release builds.

Enforced by Qlik

  • Identity and login, including your identity provider
  • Tenant admin approves the app once
  • Answers Entitlement per person
  • Space, Assistant and Knowledge Base access per person
  • Rate limits and service guardrails
Open before productionEmbedded view hardening (navigation, storage, sign-out teardown) · token bridge has no Qlik contract · CDN runtime not pinned · iOS and physical-device acceptance · build-time dependency audit findings

Show what is protected, who is responsible for what, and what is still open. Do not claim the app is production-ready or compliant.

Responsibility split

  • Qlik: identity, login, entitlements, space and Knowledge Base permissions, rate limits, the data itself.
  • App (MTC): where tokens live on the phone, what is cached, the device lock, screen-capture protection, and that tokens go only to the Tenant.
  • Client: Tenant admin approval, who gets an Answers Entitlement and space access, MDM policy if used.

Evidence (source files)

  • Tenant-only URLs: src/qlik/classic/http.ts (qlikUrl). No content on device: ADR-0007; WebView incognito and cacheEnabled=false in src/qlik-embed/qlik-embed-host.tsx.
  • Lock: src/components/lock-gate.tsx (default 5-minute background timeout, MDM can change it). Capture: src/config/screen-capture.ts.

  • Offline apps, alerts, push notifications, monitored charts.

Objective · 10 min

Answer briefly and honestly. If unsure, say so and follow up in writing.

Why use this instead of native Qlik Analytics?

Use both. Qlik Analytics is best for full dashboards, offline and alerts. Qurio adds native Qlik Answers on mobile without a browser, with History, sources and feedback, in an interface we can tailor.

What additional value does it provide?

Conversational answers with Citations on a phone; one place for Assistants and Analytics Apps; no Answer content on the device; lock and capture protection on by default.

How does Qlik Answers integrate?

Legacy Assistants: native screens over Qlik's published Assistants REST API, with streamed Answers. Agentic Assistants: Qlik's own qlik-embed UI inside the app, using the same sign-in (proof of concept).

How is user data protected?

Each person signs in as themselves, so Qlik enforces their permissions. The access token stays in memory, the refresh token in the device keystore. Sign-out revokes tokens. No Answers are stored. Embedded hardening is still open (ticket 24).

What are the current limitations?

Analytics viewer and Agentic Assistant are PoC; two OAuth regions (ap, sg); one Tenant at a time; online only; no alerts; internal builds only.

What happens when Qlik APIs or services change?

Lists and Legacy chat use published, stable REST APIs. The embedded token bridge has no Qlik contract and loads runtime v1 from a CDN, so we re-check it after Qlik runtime updates. Pinning the runtime is a proposed improvement.

How difficult is it to maintain?

Moderate. One codebase for iOS and Android, no server. MTC owns regional OAuth clients, the Android managed-config module, and re-checks of embedded views. The repository has unit tests, lint and type checks in CI.

Is it ready for production?

No, not yet. The native Assistant experience is the most mature part. Production needs device acceptance on iOS and physical Android, embedded hardening, production OAuth clients (GitHub issue 8), and a production build profile.

What are the recommended next steps?

Your feedback and priorities today. Then, if you agree: security validation, performance testing, user acceptance testing, and a deployment readiness assessment.
